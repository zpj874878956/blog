# 一、先建立 Kubernetes 的整体认知

一个 Kubernetes 集群，最核心可以拆成三层：

```text
                     用户 / CI/CD / Rancher
                              |
                         kubectl / API
                              |
                              v
+------------------------------------------------------+
|                Control Plane 控制平面                 |
|                                                      |
|  kube-apiserver                                      |
|       |                                              |
|       +------ etcd                                   |
|       |                                              |
|       +------ scheduler                              |
|       |                                              |
|       +------ controller-manager                     |
+------------------------------------------------------+
                   |             |
             --------------------------
             |                        |
             v                        v
+-------------------------+   +-------------------------+
| Worker Node 01          |   | Worker Node 02          |
|                         |   |                         |
| kubelet                 |   | kubelet                 |
| containerd              |   | containerd              |
| CNI 网络                 |   | CNI 网络                 |
| kube-proxy              |   | kube-proxy              |
|                         |   |                         |
| Pod                     |   | Pod                     |
| ├─ container            |   | ├─ container            |
| └─ container            |   | └─ container            |
+-------------------------+   +-------------------------+
```

所以 Kubernetes 不是某一个程序，而是**一整套分布式组件共同组成的集群管理系统**。

------

# 二、什么叫 Kubernetes 集群

Kubernetes Cluster，就是一组服务器共同组成的 Kubernetes 环境。

例如：

```text
k8s-master01   192.168.1.10
k8s-master02   192.168.1.11
k8s-master03   192.168.1.12

k8s-node01     192.168.1.21
k8s-node02     192.168.1.22
k8s-node03     192.168.1.23
```

前三台可能作为 Control Plane，后三台运行业务。

但 Kubernetes 并不强制要求这样分。

比如你见到的 Rancher/RKE2 环境，很可能是：

```text
node01
control-plane
etcd
worker

node02
control-plane
etcd
worker

node03
control-plane
etcd
worker
```

也就是说同一台服务器既可以负责管理集群，也可以运行应用。

因此：

**Cluster = 一套 Kubernetes 管理范围内的所有 Node、Pod、Service、存储、网络、配置等资源的集合。**

------

# 三、Control Plane 是什么

Control Plane 可以理解成 Kubernetes 的**大脑**。

它主要负责：

```text
接收请求
    ↓
保存集群状态
    ↓
决定 Pod 放到哪里
    ↓
监控实际状态
    ↓
发现和期望状态不一致
    ↓
自动修复
```

Control Plane 中最核心的组件是：

| 组件                     | 作用                       |
| ------------------------ | -------------------------- |
| kube-apiserver           | Kubernetes 的统一 API 入口 |
| etcd                     | 保存 Kubernetes 集群数据   |
| kube-scheduler           | 决定 Pod 放在哪台 Node     |
| kube-controller-manager  | 维护资源的期望状态         |
| cloud-controller-manager | 对接云厂商资源，可选       |

其中前四个一定要重点掌握。

------

# 四、kube-apiserver：整个 Kubernetes 的入口

几乎所有 Kubernetes 操作最终都会进入：

```text
kube-apiserver
```

例如执行：

```bash
kubectl get pod
```

实际流程并不是：

```text
kubectl
  ↓
直接访问 node
```

而是：

```text
kubectl
   ↓
kube-apiserver
   ↓
认证 Authentication
   ↓
鉴权 Authorization
   ↓
Admission
   ↓
查询 etcd
   ↓
返回 Pod 信息
```

你执行：

```bash
kubectl apply -f nginx.yaml
```

也是：

```text
kubectl
   ↓
apiserver
   ↓
校验 YAML
   ↓
写入 etcd
```

所以可以记住一句话：

> **Kubernetes 中几乎所有操作都围绕 kube-apiserver 展开。**

这也是为什么 kubeconfig 中最重要的内容之一就是：

```yaml
server: https://192.168.1.10:6443
```

`6443` 通常就是 kube-apiserver。

------

# 五、etcd：Kubernetes 的数据库

etcd 是一个分布式 KV 数据库。

Kubernetes 的核心状态几乎都存在 etcd 里面。

例如：

```text
有哪些 Node
有哪些 Pod
有哪些 Deployment
有哪些 Service
有哪些 ConfigMap
有哪些 Secret
有哪些 Namespace
有哪些 RBAC
有哪些 CRD
```

都保存在 etcd。

因此：

```text
etcd 数据丢失
≈
Kubernetes 集群控制面数据丢失
```

虽然运行中的容器短时间可能还在，但 Kubernetes 已经不知道自己管理了什么。

所以生产环境经常：

```text
3 个 Control Plane
+
3 个 etcd member
```

例如：

```text
master01  etcd
master02  etcd
master03  etcd
```

形成 etcd 三节点集群。

运维上非常重要的一项工作就是：

```bash
etcd snapshot save
```

也就是定期备份 etcd。

------

# 六、Scheduler：Pod 调度器

假设你创建：

```yaml
replicas: 3
```

需要运行三个 Pod。

集群里有：

```text
node01
node02
node03
node04
```

到底把 Pod 放在哪台机器？

就是：

```text
kube-scheduler
```

负责。

Scheduler 会综合考虑：

```text
CPU
内存
污点 Taint
容忍 Toleration
亲和性 Affinity
反亲和性 AntiAffinity
NodeSelector
PV 拓扑
Pod 拓扑
资源 Request
```

例如 Pod：

```yaml
resources:
  requests:
    cpu: "2"
    memory: "4Gi"
```

那么 Scheduler 就要寻找：

```text
至少还能分配 2 CPU + 4Gi 内存的 Node
```

如果所有 Node 都不满足：

```text
Pod = Pending
```

所以以后看到：

```bash
kubectl get pod
```

发现：

```text
myapp-xxx   0/1   Pending
```

第一反应应该是：

```bash
kubectl describe pod myapp-xxx
```

查看：

```text
Events
```

很可能是 Scheduler 找不到合适节点。

------

# 七、Controller Manager：Kubernetes 自动恢复的核心

这是理解 Kubernetes 最重要的部分之一。

比如定义：

```yaml
replicas: 3
```

意思是：

> 我希望永远有 3 个 Pod。

假设当前：

```text
Pod1 Running
Pod2 Running
Pod3 Running
```

某台服务器挂了：

```text
Pod3 消失
```

现在：

```text
期望状态：3
实际状态：2
```

Controller 会发现：

```text
3 != 2
```

于是创建一个新 Pod。

重新达到：

```text
期望状态：3
实际状态：3
```

这就是 Kubernetes 非常核心的思想：

# Desired State

也就是：

> **声明期望状态，而不是一步一步告诉 Kubernetes 怎么操作。**

传统运维可能是：

```text
启动 nginx
检查 nginx
发现挂了
重新启动 nginx
```

Kubernetes 的思路是：

```yaml
replicas: 3
```

然后告诉 Kubernetes：

> 我要三个副本，至于怎么保证三个副本存在，是你的事情。

------

# 八、Reconciliation Loop：调谐循环

这是 Kubernetes、Operator、Controller 最底层的设计思想。

可以简单理解为：

```text
期望状态 Desired State
        ↓
      比较
        ↓
实际状态 Current State
        ↓
不一致？
   ↓        ↓
  是        否
  ↓
执行操作
  ↓
重新比较
```

例如：

```text
期望 Pod = 5

实际 Pod = 3
```

Controller：

```text
创建 2 个
```

如果：

```text
实际 Pod = 7
```

Controller：

```text
删除 2 个
```

最终维持：

```text
实际 = 期望
```

所以你以后理解：

```text
Deployment
StatefulSet
DaemonSet
Operator
HPA
```

都可以从“Controller 不断调谐资源”的角度理解。

------

# 九、Node：Kubernetes 中的服务器

Node 基本可以理解为：

> Kubernetes 管理的一台服务器。

执行：

```bash
kubectl get nodes
```

可能看到：

```text
NAME       STATUS   ROLES
master01   Ready    control-plane
node01     Ready    worker
node02     Ready    worker
```

Node 上最重要的几个组件：

```text
kubelet
containerd
CNI
kube-proxy
```

------

# 十、kubelet：Node 上的管理员

kubelet 运行在每个 Node 上。

可以理解成：

> Control Plane 派驻在服务器上的执行人员。

例如：

```text
apiserver：
node01 上应该运行 nginx Pod

↓

kubelet：
收到

↓

containerd：
创建 nginx 容器
```

所以：

```text
Control Plane
       ↓
    kubelet
       ↓
 containerd
       ↓
    container
```

当某台 Node 的 kubelet 出问题时：

```bash
kubectl get node
```

很可能出现：

```text
NotReady
```

------

# 十一、Container Runtime：真正运行容器的组件

Kubernetes 本身并不直接运行容器。

真正运行容器的是：

```text
containerd
CRI-O
```

以前 Docker 也可以直接作为 Kubernetes runtime 使用，现在主流一般是：

```text
containerd
```

所以关系是：

```text
Kubernetes
    ↓
kubelet
    ↓
CRI
    ↓
containerd
    ↓
runc
    ↓
Linux namespace/cgroup
```

也就是说：

> Kubernetes 是容器编排系统，不是容器运行时。

------

# 十二、Pod：Kubernetes 最核心的运行单位

这是 Kubernetes 最重要的资源之一。

很多初学者会认为：

```text
Kubernetes 管理 Container
```

严格来说不准确。

Kubernetes 主要管理的是：

```text
Pod
```

然后：

```text
Pod
 └── Container
```

例如：

```yaml
apiVersion: v1
kind: Pod

spec:
  containers:
  - name: nginx
    image: nginx:1.27
```

结构是：

```text
Pod
└── nginx container
```

一个 Pod 也可以有多个 Container：

```text
Pod
├── java-app
└── log-agent
```

Pod 中的容器：

```text
共享 IP
共享网络 namespace
可以共享 Volume
可以通过 localhost 通信
```

所以：

```text
Pod IP = 10.42.1.15
```

两个 Container 都使用这个网络空间。

------

# 十三、为什么 Kubernetes 不建议直接创建 Pod

虽然你可以：

```yaml
kind: Pod
```

但生产环境很少直接这样做。

因为：

```text
Pod 被删除
↓
没有 Controller
↓
不会重新创建
```

所以通常是：

```text
Deployment
   ↓
ReplicaSet
   ↓
Pod
```

例如：

```bash
kubectl get deployment
kubectl get rs
kubectl get pod
```

背后的关系就是：

```text
Deployment
     |
     v
ReplicaSet
     |
     +---- Pod
     +---- Pod
     +---- Pod
```

------

# 十四、Deployment 是什么

Deployment 主要用于：

> 无状态应用。

例如：

```text
Java
Go
Python
Node.js
Nginx
API 服务
Web 服务
```

典型结构：

```yaml
kind: Deployment

spec:
  replicas: 3
```

代表：

```text
我希望运行 3 个应用实例
```

Deployment 还负责：

```text
滚动升级
滚动回滚
副本管理
版本管理
```

例如：

```text
v1
Pod Pod Pod
```

升级：

```text
v2
```

Deployment 会逐渐：

```text
删除旧 Pod
创建新 Pod
```

而不是一次性全部停掉。

------

# 十五、ReplicaSet 是什么

ReplicaSet 最核心的职责只有一个：

> 保证指定数量的 Pod 存活。

例如：

```text
replicas = 3
```

实际：

```text
2
```

就创建一个。

实际：

```text
4
```

就删除一个。

但通常不会直接创建 ReplicaSet。

一般：

```text
Deployment
   ↓
ReplicaSet
   ↓
Pod
```

Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod。

------

# 十六、StatefulSet 是什么

StatefulSet，简称：

```text
STS
```

主要用于：

> 有状态应用。

例如：

```text
MySQL
Redis
MongoDB
Kafka
ZooKeeper
Elasticsearch
```

Deployment 的 Pod 通常叫：

```text
myapp-6bffb7dd79-abcde
myapp-6bffb7dd79-xzyyy
```

Pod 身份没有太大区别。

StatefulSet：

```text
mysql-0
mysql-1
mysql-2
```

名字固定。

而且通常：

```text
mysql-0 → pvc-mysql-0
mysql-1 → pvc-mysql-1
mysql-2 → pvc-mysql-2
```

每个实例都有自己的持久化存储。

所以 StatefulSet 重点提供：

```text
稳定名称
稳定网络身份
稳定存储
有序启动
有序停止
```

------

# 十七、DaemonSet 是什么

DaemonSet，简称：

```text
DS
```

含义：

> 每台满足条件的 Node 都运行一个 Pod。

例如集群：

```text
node01
node02
node03
```

DaemonSet 会：

```text
node01 → agent Pod
node02 → agent Pod
node03 → agent Pod
```

非常适合：

```text
日志采集
监控 agent
网络插件
存储插件
安全 agent
```

例如经常看到：

```text
node-exporter
fluent-bit
filebeat
calico-node
```

很多就是 DaemonSet。

------

# 十八、Job 和 CronJob

Job 用于：

> 一次性任务。

例如：

```text
数据库初始化
数据迁移
批处理
文件处理
```

任务完成：

```text
Completed
```

就结束。

CronJob 则是：

> 定时创建 Job。

比如：

```text
每天 02:00 数据备份
每天清理一次临时文件
每小时生成报表
```

关系：

```text
CronJob
   ↓
Job
   ↓
Pod
```

------

# 十九、Service：为什么需要 Service

这是 Kubernetes 网络最重要的资源之一。

假设：

```text
Java Deployment
replicas = 3
```

Pod：

```text
java-abc   10.42.1.5
java-def   10.42.2.7
java-xyz   10.42.3.9
```

问题来了：

> 客户端到底访问哪个 Pod？

更麻烦的是 Pod 重启后：

```text
10.42.1.5
```

可能变成：

```text
10.42.4.17
```

所以不能直接依赖 Pod IP。

这时候使用：

```text
Service
```

例如：

```text
Service IP：

10.43.10.100
```

后端：

```text
         Service
     10.43.10.100
          |
    ----------------
    |       |      |
   Pod     Pod    Pod
```

于是应用只访问：

```text
http://my-service
```

而不用关心具体 Pod。

------

# 二十、Service 的几个重要类型

最常见的是：

| 类型             | 用途                       |
| ---------------- | -------------------------- |
| ClusterIP        | Kubernetes 集群内部访问    |
| NodePort         | 通过 NodeIP:Port 对外访问  |
| LoadBalancer     | 使用负载均衡器对外提供服务 |
| ExternalName     | DNS 映射                   |
| Headless Service | StatefulSet 等场景         |

最常用的是：

```text
ClusterIP
```

例如：

```yaml
type: ClusterIP
port: 80
targetPort: 8080
```

就是：

```text
客户端
  ↓ 80
Service
  ↓ 8080
Pod
```

------

# 二十一、Ingress 和 Gateway

如果有：

```text
user-service
order-service
pay-service
admin-service
```

总不能全部暴露：

```text
NodePort
```

一般在前面加：

```text
Ingress Controller
```

例如：

```text
Internet
   ↓
LoadBalancer
   ↓
Ingress Nginx
   ↓
--------------------------
|           |            |
user       order        pay
Service    Service      Service
```

根据：

```text
api.example.com/user
api.example.com/order
api.example.com/pay
```

路由到不同 Service。

新一点的 Kubernetes 环境则越来越多使用：

```text
Gateway API
```

可以简单理解：

```text
Ingress
  ↓
更现代、更标准化
  ↓
Gateway API
```

------

# 二十二、Namespace 是什么

Namespace 可以理解成：

> Kubernetes 集群里面的逻辑隔离空间。

例如：

```text
default
monitoring
logging
middleware
production
dev
test
```

执行：

```bash
kubectl get pod -n monitoring
```

只看 monitoring。

```bash
kubectl get pod -A
```

看全部 Namespace。

不过要特别注意：

并不是所有 Kubernetes 资源都属于 Namespace。

例如：

```text
Pod              Namespaced
Deployment       Namespaced
Service          Namespaced
ConfigMap        Namespaced
Secret           Namespaced

Node             Cluster Scoped
PV               Cluster Scoped
Namespace        Cluster Scoped
StorageClass     Cluster Scoped
CRD              Cluster Scoped
```

所以：

```bash
kubectl get all -n monitoring
```

并不代表“monitoring 的所有 Kubernetes 资源”。

而且 `get all` 本身也不是“真正所有资源”。

------

# 二十三、Label 和 Selector

这是 Kubernetes 资源关联关系的基础。

例如 Pod：

```yaml
labels:
  app: nginx
```

Service：

```yaml
selector:
  app: nginx
```

意思：

```text
Service
selector:
app=nginx
    ↓
找到所有
label:
app=nginx
    ↓
Pod
```

所以很多问题例如：

```text
Service 访问不到 Pod
```

就应该检查：

```bash
kubectl get svc xxx -o yaml

kubectl get pod --show-labels

kubectl get endpoints xxx
```

看：

```text
selector
    ↓
label
```

能否匹配。

------

# 二十四、ConfigMap

ConfigMap 用于保存：

> 非敏感配置。

例如：

```text
application.yml
nginx.conf
环境变量
URL
日志级别
功能开关
```

例如：

```yaml
data:
  LOG_LEVEL: INFO
  REDIS_HOST: redis
```

Pod 可以：

```text
ConfigMap
   ↓
环境变量
```

或者：

```text
ConfigMap
   ↓
Volume
   ↓
/etc/app/config.yaml
```

------

# 二十五、Secret

Secret 用于敏感配置，例如：

```text
密码
Token
TLS 证书
Registry 凭证
数据库用户名密码
```

例如：

```text
mysql-password
registry-secret
tls-secret
```

需要注意：

Kubernetes 默认 Secret 并不是“超级安全的加密保险箱”。

很多情况下只是：

```text
Base64
```

编码，再配合 etcd encryption、RBAC 等提高安全性。

------

# 二十六、PV、PVC、StorageClass

这是 Kubernetes 存储体系非常重要的一部分。

可以这样理解：

```text
Pod
 ↓
PVC
 ↓
PV
 ↓
真正存储
```

例如：

```text
Pod
 ↓
PVC mysql-data
 ↓
PV pvc-abcd1234
 ↓
NFS / Ceph / Longhorn / EBS / 本地磁盘
```

PVC：

> 应用提出“我要多少存储”。

例如：

```yaml
resources:
  requests:
    storage: 100Gi
```

PV：

> Kubernetes 中实际提供的存储资源。

StorageClass：

> 告诉 Kubernetes 怎么自动创建 PV。

关系：

```text
PVC:
我要 100Gi
   ↓
StorageClass:
使用 ceph-rbd
   ↓
CSI:
去 Ceph 创建磁盘
   ↓
PV
   ↓
绑定 PVC
   ↓
Pod mount
```

------

# 二十七、CNI：Kubernetes 容器网络

Kubernetes 自己并没有实现具体网络。

通常使用 CNI，例如：

```text
Calico
Canal
Cilium
Flannel
```

CNI 主要解决：

```text
Pod 如何获得 IP
Pod 与 Pod 如何通信
Node 与 Pod 如何通信
网络路由
NetworkPolicy
```

例如：

```text
node01
Pod A 10.42.1.5
       |
       |
       v
node02
Pod B 10.42.2.8
```

CNI 负责让：

```text
10.42.1.5
```

可以访问：

```text
10.42.2.8
```

------

# 二十八、kube-proxy 是什么

kube-proxy 主要负责 Service 流量转发。

例如：

```text
Service
10.43.10.100:80
```

后面有：

```text
10.42.1.5:8080
10.42.2.6:8080
10.42.3.7:8080
```

kube-proxy 会维护相关转发规则。

传统实现包括：

```text
iptables
IPVS
```

流程大致：

```text
访问 ClusterIP
      ↓
kube-proxy 创建的转发规则
      ↓
某一个 Pod IP
```

现代 Cilium 等方案也可以使用 eBPF 替代传统 kube-proxy 能力。

------

# 二十九、CoreDNS

Kubernetes 内部基本不会让你直接写：

```text
10.43.10.100
```

而是：

```text
mysql
redis
user-service
```

这个 DNS 解析通常由：

```text
CoreDNS
```

完成。

例如 Service：

```text
Namespace: middleware
Service: redis
```

完整 DNS：

```text
redis.middleware.svc.cluster.local
```

同 Namespace 可以直接：

```text
redis
```

跨 Namespace：

```text
redis.middleware
```

或者：

```text
redis.middleware.svc.cluster.local
```

------

# 三十、Requests 和 Limits

这是生产 Kubernetes 集群运维必须掌握的概念。

例如：

```yaml
resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    cpu: "2"
    memory: 2Gi
```

含义：

```text
requests
=
调度时认为这个 Pod 至少需要多少资源
```

而：

```text
limits
=
Pod 最多允许使用多少
```

例如：

```text
requests CPU 500m
limits CPU 2
```

意思并不是固定使用 0.5 CPU。

而是：

```text
调度时预留 0.5 CPU
实际最多可以使用 2 CPU
```

内存如果超过：

```text
memory limit
```

通常：

```text
OOMKilled
```

------

# 三十一、Probe：健康检查

Kubernetes 主要有三种 Probe：

| Probe          | 作用             |
| -------------- | ---------------- |
| startupProbe   | 应用是否启动完成 |
| readinessProbe | 是否可以接收流量 |
| livenessProbe  | 应用是否还活着   |

例如：

```text
readinessProbe 失败
```

Pod 可能仍然：

```text
Running
```

但：

```text
Service 不再把流量转发给它
```

而：

```text
livenessProbe
```

持续失败：

```text
kubelet 重启 container
```

这是运维排查：

```text
Pod Running
但是访问异常
```

时很重要的地方。

------

# 三十二、RBAC

RBAC 就是 Kubernetes 权限控制。

核心对象：

```text
User / ServiceAccount

        ↓

Role / ClusterRole

        ↓

RoleBinding / ClusterRoleBinding
```

例如：

```text
张三
只能查看 monitoring Namespace
```

可以：

```text
Role
+
RoleBinding
```

而：

```text
可以查看整个集群 Node
```

通常使用：

```text
ClusterRole
+
ClusterRoleBinding
```

这也是为什么有时候 kubectl 会报：

```text
Forbidden
User xxx cannot list resource pods
```

本质就是 RBAC 权限不足。

------

# 三十三、ServiceAccount

ServiceAccount 可以简单理解成：

> Pod 在 Kubernetes 集群里的身份。

比如一个程序运行在 Pod 中，需要：

```text
读取 Pod
读取 ConfigMap
更新某个 CRD
```

不应该给它管理员 kubeconfig。

而应该：

```text
ServiceAccount
      ↓
Role / ClusterRole
      ↓
RoleBinding
```

Operator 基本都会大量使用 ServiceAccount。

# 三十四、CRD 是什么

Kubernetes 原生认识：

```text
Pod
Deployment
Service
ConfigMap
Secret
PVC
```

但是如果你希望 Kubernetes 认识：

```yaml
kind: MySQLCluster
```

怎么办？

就可以创建：

```text
CRD
CustomResourceDefinition
```

定义一种新的 Kubernetes 资源。

例如：

```yaml
apiVersion: mysql.example.com/v1
kind: MySQLCluster

spec:
  replicas: 3
  storage: 100Gi
```

这样：

```bash
kubectl get mysqlcluster
```

就可以操作自定义资源。

# 三十五、Operator 是什么

Operator 可以理解成：

> CRD + Controller + 某个领域的运维知识。

例如 MySQL Operator：

```text
你：
创建 MySQLCluster

      ↓

Operator:
创建 StatefulSet
创建 Service
创建 PVC
初始化主从
监控状态
处理故障
扩容
升级
```

所以 Operator 本质还是前面讲的：

```text
Desired State
      ↓
Controller
      ↓
Reconciliation
```

只不过把 Kubernetes Controller 的思想扩展到了具体应用。

# 三十六、一个 Java 应用到底是怎么在 Kubernetes 运行起来的

把所有概念串起来看，会非常清楚。

你执行：

```bash
kubectl apply -f app.yaml
```

假设是：

```text
Deployment
replicas = 3
```

完整流程大概是：

```text
kubectl
   ↓
kube-apiserver
   ↓
认证、鉴权
   ↓
Deployment 写入 etcd
   ↓
Deployment Controller
   ↓
创建 ReplicaSet
   ↓
ReplicaSet Controller
   ↓
创建 3 个 Pod
   ↓
Scheduler
   ↓
Pod1 → node01
Pod2 → node02
Pod3 → node03
   ↓
各节点 kubelet
   ↓
containerd
   ↓
拉镜像
   ↓
创建 Container
   ↓
CNI
   ↓
分配 Pod IP
   ↓
Probe 检查
   ↓
Ready
   ↓
Service
   ↓
把流量转发到 Pod
```

如果外部访问：

```text
用户
 ↓
DNS
 ↓
LoadBalancer
 ↓
Ingress / Gateway
 ↓
Service
 ↓
Pod
 ↓
Java Container
```

这实际上就是 Kubernetes 最重要的一条主线。

# 三十七、Kubernetes YAML 到底是什么

你看到大量 Kubernetes YAML，其实基本都是同一种结构：

```yaml
apiVersion:
kind:
metadata:
spec:
status:
```

例如：

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: java-app
  namespace: production

spec:
  replicas: 3
```

可以理解成：

```text
apiVersion
=
这个资源属于 Kubernetes 哪套 API

kind
=
资源类型

metadata
=
资源叫什么、在哪个 namespace、有什么标签

spec
=
我希望它变成什么样

status
=
它现在实际上是什么样
```

其中最核心就是：

```text
spec
=
Desired State

status
=
Current State
```

这两个概念一理解，很多 Kubernetes 资源都会变简单。

因为 Kubernetes 是：

```text
Controller 驱动
+
事件驱动
+

```

所以排障时：

```bash
kubectl describe pod xxx
```

最下面：

```text

```

经常非常重要。

比如：

```text
FailedScheduling

```

这些信息可以直接告诉你：

```text
调度问题

```

# 三十九、把 Kubernetes 资源分成 8 大类最好记

我建议把几十种 Kubernetes 资源在脑子里归成下面这个体系：

| 类别     | 常见资源                                 | 主要作用        |
| -------- | ---------------------------------------- | --------------- |
| 计算     | Pod                                      | 运行容器        |
| 工作负载 | Deployment、STS、DS、Job、CronJob        | 管理 Pod        |
| 网络     | Service、Ingress、Gateway、NetworkPolicy | 服务通信        |
| 配置     | ConfigMap、Secret                        | 应用配置        |
| 存储     | PV、PVC、StorageClass                    | 持久化数据      |
| 权限     | SA、Role、ClusterRole、Binding           | RBAC            |
| 集群     | Node、Namespace                          | 集群组织        |
| 扩展     | CRD、Operator                            | 扩展 Kubernetes |

以后看到陌生资源，可以先问：

> 它属于这 8 类里的哪一类？

理解速度会快很多。

# 四十、最终要建立的 Kubernetes 脑图

建议你最后把 Kubernetes 记成下面这张图：

```text
                        Kubernetes Cluster
                               |
          +--------------------+-------------------+
          |                                        |
    Control Plane                              Worker Node
          |                                        |
    kube-apiserver                             kubelet
          |                                        |
    +-----+--------+                        containerd
    |              |                              |
   etcd        scheduler                         Pod
    |              |                              |
controller-manager |                         Container
    |              |
    +------+-------+
           |
        Desired
         State


应用资源：

Deployment
    ↓
ReplicaSet
    ↓
Pod
    ↓
Container


访问链路：

用户
 ↓
Ingress / Gateway
 ↓
Service
 ↓
Pod


存储链路：

Pod
 ↓
PVC
 ↓
PV
 ↓
CSI
 ↓
NFS / Ceph / 云盘


配置链路：

ConfigMap / Secret
        ↓
       Pod


权限链路：

User / ServiceAccount
        ↓
Role / ClusterRole
        ↓
RoleBinding / ClusterRoleBinding


扩展机制：

CRD
 ↓
Custom Resource
 ↓
Operator / Controller
 ↓
实际 Kubernetes 资源
```

如果只记住 Kubernetes 最核心的 **5 个思想**，我建议记：

**第一，Kubernetes 管理的是“期望状态”，不是一条条命令。**

**第二，Controller 会不断比较 `spec` 和 `status`，让实际状态趋近于期望状态。**

**第三，Pod 是最小调度单位，Deployment/STS/DS 等 Controller 才是真正用于生产管理 Pod 的资源。**

**第四，Service 解决 Pod 不稳定的问题，Ingress/Gateway 解决外部流量入口问题。**

**第五，Kubernetes 本质是 API 驱动的分布式系统：kubectl、Rancher、Operator、CI/CD 最终基本都是在操作 kube-apiserver。**

掌握这套主线后，再去学习 `Deployment → Service → Ingress → PVC → ConfigMap → RBAC → CRD/Operator`，就不会再觉得 Kubernetes 是几十个互不相关的资源，而是会发现它们实际上组成了一套非常完整的系统。
